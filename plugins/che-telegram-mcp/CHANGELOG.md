## [Unreleased]

### Security
- The wrappers install a downloaded binary only when its sha256 matches ([#50](https://github.com/PsychQuant/che-msg/issues/50)). Each wrapper pins the sha256 of its release asset next to `DESIRED_VERSION` (`SHA256_PIN`, used while `SHA256_PIN_VERSION` equals `DESIRED_VERSION`); a release sets both after its build (RELEASING.md step 8, `make check-sha256`). Both wrappers pin 0.8.0, which was released without `.sha256` files: each pin is the sha256 digest GitHub lists for that asset. A wrapper with no pin for its version, or a malformed one, downloads nothing and says so; the digest GitHub lists next to an asset is never used instead, because a replaced asset would match it too. A file that does not match is removed and the installed binary and its version record stay as they were. The no-op `xattr -dr com.apple.quarantine` line is gone (curl sets no quarantine attribute). Layout check (b3) refuses a wrapper whose pin is missing, not 64 lowercase hex digits, or for another version, and `check-versions.sh` also one that does not equal the release build's `.sha256`.

### Changed
- README: a Requirements section: macOS 26 or later ([#91](https://github.com/PsychQuant/che-msg/issues/91)). The binaries after v0.8.0 are built for macOS 26; the v0.8.0 binaries most likely do not start on macOS 13–15 either unless Xcode 26 or later is installed.
- **Behavior change:** the download runs in the background, never on the startup path ([#67](https://github.com/PsychQuant/che-msg/issues/67)). Claude Code waits about 30 seconds for a server to start; the 238 MB telegram-all download took minutes on a slow link, so the start timed out, the wrapper was stopped before its `mv`, and the next start downloaded again from zero. Now a wrapper with a binary it can run (telegram-all: 0.7.0 or later) starts it at once and the new version is used from the first start after it is installed. With none, it waits up to 3 seconds (`CHE_TELEGRAM_MCP_INSTALL_WAIT` sets another wait, up to 600) and then stops saying the download goes on in the background; both wrappers write that message to stderr and answer `initialize` with it as a JSON-RPC error (the bot wrapper did not answer `initialize` at all before; its error links a new README section, "When telegram-bot does not start"). The download runs in a session of its own (perl's `setsid`), so it outlives the wrapper and a signal to the wrapper's process group, and writes to `~/bin/.che-telegram-mcp-download/<Binary>.log`. A complete partial file whose sha256 matches is installed without downloading again. README: "How wrappers work", "Auto-upgrade", a new "A slow link" (`CHE_TELEGRAM_MCP_INSTALL_WAIT` with Claude Code's `MCP_TIMEOUT`) and "When telegram-all does not start".
- **Behavior change:** the wrappers download only the release of `DESIRED_VERSION`, from its own URL (`releases/download/v<version>/<Binary>`), and never fall back to `releases/latest` ([#50](https://github.com/PsychQuant/che-msg/issues/50)). Before, a pinned version without the asset installed the latest release's file and recorded the pinned version for it, so that machine never fetched the real release afterwards. The release API is not asked. README "How wrappers work" and "Manual install" (which now checks the sha256) describe it.
- **Behavior change:** once a binary is installed in `~/bin`, both wrappers download only when its version record (`~/bin/.<Binary>.version`) is older than `DESIRED_VERSION`, missing, or not a plain `x.y.z`; a binary newer than the pin is kept ([#83](https://github.com/PsychQuant/che-msg/issues/83)). Before, any difference triggered a download, so a session still running an older plugin put its older binary back over a newer one. Sessions still running plugin 1.7.0 or earlier keep the old behavior until they are restarted. A later plugin that lowers the pin no longer downgrades an installed binary, and a version record set below the pin does not stick, because the wrapper downloads the pinned version again; README "Auto-upgrade" explains.
- The version record is read with only surrounding whitespace removed, so a record such as `9. 0.0`, or one spread over two lines, counts as not `x.y.z` instead of being joined into a version. When the record is missing or not `x.y.z`, the download message says so instead of printing it as a version.
- README: "Auto-upgrade" gives the telegram-all minimum as 0.7.0 (it said 0.6.0), and the manual-install and version notes no longer say that any version difference triggers a download.
- `/che-telegram-mcp:auth` logs in with `auth_run` and follows `auth_status.next_step` (it may now call `auth_run` without a prompt in the turn you invoke it); it no longer walks through the step tools first, never calls `logout` without asking, and says when a typed 2FA password stays in the transcript ([#48](https://github.com/PsychQuant/che-msg/issues/48)). The step tools stay as a fallback.

### Tests
- `test-wrapper-incomplete-plugin.sh` (new, [#59](https://github.com/PsychQuant/che-msg/issues/59)): both wrappers, from copies whose `lib/` lacks a file. With `lib/download.sh` missing, `initialize` gets the incomplete-plugin error (-32000) for its id and `server/discover` gets -32601; with `lib/startup-error.sh` missing (or, for telegram-all, unreadable), the error carries `id` null whatever the first message is. The reason is on stderr and no binary starts.
- `test-wrapper-first-request.sh` (new, [#59](https://github.com/PsychQuant/che-msg/issues/59)): `server/discover` as the first request gets one -32601 answer for its id, numeric or string, and never the -32000 startup error, from telegram-all (missing credentials, a failed and a still-running first download, a 0.6.0 binary) and telegram-bot (a failed and a still-running first download); stderr names the cause, and no binary is started. A notification first, `initialize` included, gets no answer; a batch gets one -32600 error with `id` null; a client that keeps stdin open without writing gets the startup error with `id` null after the 2-second read. With a binary to run, both wrappers hand the request to the server as its first line. `lib/startup-error.sh`'s reader is checked on its own for each kind of first line (ids null, 1.5, -7, `""` and one with an escaped quote among them), and without a `jq` of 1.7 or later, where every line gets the startup error with `id` null. Ids 9007199254740993 and 3.141592653589793238462643383279 are echoed as written, and fake `jq`s check the version rule: a `jq-1.6` alone, or one whose version cannot be read, is not used; `/usr/bin/jq` is tried before the `jq` on `PATH`, and a `jq-1.6` there is passed over.
- `test-wrapper-background-download.sh` (new, [#67](https://github.com/PsychQuant/che-msg/issues/67)): both wrappers, each in a process group of its own that is stopped as a whole; both answer `initialize` with a JSON-RPC error on a first install, which the download and checksum tests check for the bot wrapper too, with its docsUrl. With a usable binary and a slow download the binary starts within 5 seconds and the download completes after the group is stopped; with nothing installed the start ends within 5 seconds saying the download goes on (telegram-all with a JSON-RPC error), and the download completes afterwards; a complete partial file is installed without a download; the download log records the install; a longer `CHE_TELEGRAM_MCP_INSTALL_WAIT` lets a first download finish. The harness exports `CHE_TELEGRAM_MCP_INSTALL_WAIT=30`, so the other tests see what a failed download is reported as on a loaded machine, and `wait_no_fetch` lets a test wait for a download left running after a hand-over.
- `test-wrapper-checksum.sh` (new, [#50](https://github.com/PsychQuant/che-msg/issues/50)): both wrappers and copies with a pin set: a matching pin installs without calling the release API; a mismatch installs nothing, leaves no partial file and keeps a usable installed binary with its record; a pin for another version, no pin and a malformed pin each download and install nothing, even when GitHub's digest matches a replaced asset; a missing pinned asset installs nothing, and no case asks the release API or `releases/latest`. Layout check (b3) with seven mutation cases.
- `test-wrapper-download.sh` (new, [#56](https://github.com/PsychQuant/che-msg/issues/56)): both wrappers, run with `/bin/bash`, against an HTTP error for the asset, a transfer cut off and resumed by the next start, a partial file of another version, every attempt failing with and without a usable binary installed, two telegram-all wrappers started together (one downloads, the other says `download already running`), a process holding the download lock (nothing is downloaded until it is gone), and the staging directory (a partial file that is a symbolic link to the installed binary leaves its bytes untouched, a log that is a link leaves its target untouched, a staging directory that is a link, a file, or of mode 777 or 755 is refused with nothing written in it, even with a genuine partial file there, and once removed is created anew with mode 700); a transfer cut off once is retried and installed in the same start, an HTTP error is tried once, and the curl options for resuming and stall detection are checked. The harness's fake curl (`tests/lib/fake_curl.sh`) can now serve the release API and an asset, an HTTP error (exit 22 with `-f`, the error page without), a transfer cut off at a given byte, a delay, and a resume from the output file's size; with nothing to serve it still fails every call. Layout check (a2): every file a wrapper sources from `lib/` exists.
- `test-wrapper-version-decision.sh` (new): both wrappers against newer, equal, older, missing, empty and malformed records, records with whitespace inside or around them, a copy pinned to 0.9.0 with record 0.10.0, and a binary outside `~/bin`; `version_at_least` is checked directly for multi-digit ordering and both regex anchors.

### Fixed
- The SessionStart hook no longer announces an older release as an upgrade ([#89](https://github.com/PsychQuant/che-msg/issues/89)). It compared the installed version record with the latest release using `!=` after removing every whitespace character, so an installed binary newer than the latest release (a hand-installed build, or any newer binary once the wrappers keep it, #83) got `⬆️ … v0.9.0 → v0.8.0 available`, and so did `0.8.0-beta` and `0. 9.0`. It now compares the way #83's wrappers do: the record trimmed of surrounding whitespace only, both versions plain `x.y.z`, ordered with `sort -V`. An older record gets the arrow; a newer one gets one line saying it is newer than the latest release; a version record that is empty or not `x.y.z` is reported as such, even offline, and the `✓` line no longer shows a version made up by removing its spaces; an odd release tag keeps the hook quiet. New test `tests/che-telegram-mcp/test-hook-version-notice.sh`.
- Both wrappers download the binary through `lib/download.sh` ([#56](https://github.com/PsychQuant/che-msg/issues/56)). An HTTP error no longer installs the error page as the binary: before, `curl -sL` exited 0 with it, the wrapper recorded the pinned version, and no later start downloaded again (telegram-all then refused the file with a wrong reason, telegram-bot ran it). The download retries a transfer that stops up to three more times, each resuming where the last one stopped (only a network failure is retried: an HTTP error, so a missing asset, is reported at once, and so is a bad certificate), gives up only when the transfer stalls instead of after 600 or 180 seconds, and writes to `<Binary>.<version>.part` in a private directory, `~/bin/.che-telegram-mcp-download` (created with mode 700; a symbolic link there is never followed, and a directory that is a link, not the user's, or of any other mode is refused, not repaired), which the next start resumes with `-C -`; a partial file of another version is removed instead of being joined to it. One process at a time writes it: the download holds an `flock` on `<Binary>.lock` in that directory from the first byte until the binary is in place, and the system releases it when the download ends, so two sessions started together no longer write the same file and a killed download leaves no lock behind; a second download stops at once with `download already running`. When nothing could be installed, the message says why (an interrupted transfer, an HTTP error, another session downloading it) and the stderr gives a manual command that downloads to a separate file and moves it into place. README: "How wrappers work" describes the download; "Manual install" downloads to `.new` with `curl -fL -C -` and moves the file into place instead of writing over the binary a running session uses.
- When a wrapper stops before starting its server, a first request other than `initialize`, such as the `server/discover` probe recent Claude Code builds send first, gets JSON-RPC "method not found" (-32601) for its own id, `null` included ([#59](https://github.com/PsychQuant/che-msg/issues/59)). Before, the wrapper answered it with the startup error meant for `initialize`. The first line is read as one JSON value with `jq` 1.7 or later (`/usr/bin/jq`, which macOS includes, then the `jq` on `PATH`; an older `jq`, such as 1.6, rounds a large numeric id it writes back), and only these kinds get their own answer: a request for another method (-32601), a notification, `initialize` included (no answer), and a batch (one -32600 "Invalid Request" error with `id` null; MCP has no batches). An `initialize` request, and an object whose `method` is missing, not a string or empty, get the startup error for their `id`; anything else (no complete line within 2 seconds, not exactly one JSON value, an `id` that is not a string, number or null, or no `jq` of 1.7 or later) gets it with `id` null. Before, the reader fell back to regular expressions without `jq`, which read fields nested in `params` and mangled ids that were not plain integers or strings. The wrapper exits 1 in every case. This applies to each refusal that answers with the startup error: telegram-all's four cases, and telegram-bot's first install and incomplete plugin (a missing bot token answers nothing). When `lib/startup-error.sh` itself cannot be read, the wrapper reads nothing from stdin and its -32000 error carries `id` null.
- The docs no longer say that `/mcp` shows why telegram-all, or on a first install telegram-bot, did not start ([#59](https://github.com/PsychQuant/che-msg/issues/59)). The wrappers write the reason to stderr and answer `initialize` with it, but the Claude Code builds checked showed only `CONNECTION_CLOSED`. README "When telegram-all does not start" now says where the reason is: the server's MCP log, as a `Server stderr:` entry (on macOS under `~/Library/Caches/claude-cli-nodejs/<project>/mcp-logs-plugin-che-telegram-mcp-telegram-all/`), and `claude --debug=mcp --debug-file <path>`; "When telegram-bot does not start", "How wrappers work" and the 1.5.0 note follow it. The README case list also names the fourth refusal, a plugin whose `lib/startup-error.sh` or `lib/download.sh` cannot be read. This corrects the 1.5.0 entry below ("so `/mcp` shows the reason").

## [1.5.0] - 2026-10-09

Several Claude Code sessions can enable telegram-all together ([che-msg#58](https://github.com/PsychQuant/che-msg/issues/58)). The wrappers pin binary `DESIRED_VERSION` 0.6.0.

### Changed
- **Behavior change:** the telegram-all wrapper takes no lock and never refuses to start because another session runs telegram-all. It keeps no shared PID file (`~/.cache/che-telegram-all-mcp.pid`) and signals only the binary it started; before, a second wrapper without a lock would have killed the first session's server. The server (binary 0.6.0) now decides who opens TDLib: it opens TDLib on first use, closes it after `CHE_TELEGRAM_ALL_IDLE_TIMEOUT` seconds idle (default 600), and while another session holds it answers the five read tools from TDLib's local cache, marked `source: local-cache`.
- **Behavior change:** the telegram-all wrapper does not run a binary older than 0.6.0 (it asks the binary for `--version`; older binaries do not answer). Before, a failed download kept the previous binary; with this wrapper's lock gone, a 0.5.x binary would open TDLib without coordinating with other sessions.
- When the wrapper stops before starting the server — API credentials missing from the Keychain, no binary to be had, or only a binary older than 0.6.0 — it answers the pending `initialize` request with a JSON-RPC error whose `data.docsUrl` links the README section "When telegram-all does not start", so `/mcp` shows the reason instead of a generic -32000.
- README: "Multiple sessions" replaces "Multi-session limitation", including how sessions still on 1.4.x coexist and how to remove a lock directory left by a killed 1.4.x wrapper. "Manual install" downloads v0.6.0 and records the installed version, so the wrapper does not download it again; "Version" states 1.5.0 and v0.6.0.

### Tests
- `test-wrapper-pid.sh` and `test-wrapper-mcp-error.sh` run the real wrapper against a private HOME (`tests/lib/wrapper_harness.sh`: fake binary, fake `security`, a fake `curl` that never reaches the network) instead of a hand-copied excerpt. They cover a second wrapper leaving the first binary running, a wrapper exit stopping only its own binary, a live `CheTelegramAllMCP` in the old shared PID file left alone, a 1.4.x lock directory not stopping the wrapper, and the three startup errors: missing credentials, no binary, and a binary older than 0.6.0 (kept after a failed download, silent on `--version`, or outside `~/bin`), each with the reason `/mcp` shows.

### Tests

Every `che-telegram-mcp@X` in the README is `@che-msg` unless it follows `uninstall`, and the README has `install che-telegram-mcp@che-msg` and `marketplace add …/che-msg` (options allowed; `--scope` takes a value). A file in `bin/` has a docsUrl; each docsUrl is exactly the README URL in its file's `GITHUB_REPO`, and its anchor matches a README heading. Files that are not regular, unreadable or over 2 MB, symlinks to directories and directories that cannot be listed are reported, not skipped. The rules parse no URLs: verify rounds 1–4 each found text that an URL parser read wrongly. The docstring lists what is deliberately not checked. Mutation cases 54 → 144.

## [1.4.1] - 2026-10-08

Documentation corrections found while verifying [#139](https://github.com/PsychQuant/psychquant-claude-plugins/issues/139), which shares this plugin's skill layout ([#138](https://github.com/PsychQuant/psychquant-claude-plugins/issues/138)). No change to the skills, wrappers or binaries; the wrappers still pin `DESIRED_VERSION` 0.5.0.

### Fixed
- The 1.4.0 README and Security note said that "in the default permission mode Claude Code asks before sending" with `send`. On recent Claude Code — every plan and provider since v2.1.284 per the changelog (the permission-modes page says v2.1.283), Pro, Max and Team plans earlier — interactive terminal and VS Code sessions start in auto mode, where a classifier reviews the call and normally nothing is asked, so most readers would have drawn the opposite conclusion. The README now names the modes as Claude Code does — Manual (config value `default`) and `acceptEdits` ask unless an allow rule matches; auto lets the classifier decide, and a matching allow rule skips the classifier; `bypassPermissions` does not ask; `dontAsk` refuses the call unless an allow rule matches — and recommends ask rules as the one setting that asks in any mode (in `dontAsk`, an ask rule refuses instead), unless a `PermissionRequest` hook or a mod approves the call: for `send_message` on both servers, since `send` does not tie itself to one, and for every other tool that sends or changes something, listed per server; or a whole-server ask rule.
- The bare-name note no longer says that `search` and `send` collide with other plugins: whether a name collides depends on what else is installed. As in 1.4.0, the bare `/auth` and the others work while no other command or skill uses the name (the 1.3.2 commands set `name` too).

### Tests
- `tests/che-telegram-mcp/test-plugin-layout.sh` (marketplace repo) now reads skill frontmatter the way Claude Code does, or refuses to. The shared `tests/lib/frontmatter_subset.py` finds the boundary as Claude Code does (the first `---` after the opening line, even inside a value, with JavaScript's whitespace class and no newline translation) and rejects a block outside the plain YAML in which PyYAML (YAML 1.1, used by the test) and Bun.YAML (YAML 1.2, used by Claude Code) read the same thing: control or line-separator characters such as NEL or U+2028, a quoted value left open on its line, `---` or `...` anywhere (bun 1.3.11 treats both as document markers even inside a value; Bun 1.4.2 does not, and the Bun 1.4.3 inside Claude Code 2.1.293 has not been tested; the ban is kept because it only rejects more), anchors, aliases, tags, block scalars, flow collections, explicit or duplicate keys. Such a block is not parsed at all; the checks that need its values fail as unverifiable. Outside that subset Claude Code could drop or rewrite `disable-model-invocation` while the test passed. `tests/frontmatter-subset-fuzz/run.sh` (needs bun) compares PyYAML with Bun.YAML on random blocks the subset accepts; its latest run (bun 1.3.11, two seeds × 50,000 blocks, 4,568 accepted) found no failed first parse and no structural, string or numeric disagreement. That is evidence for its generator, not a proof: verify round 5 of #139 found values starting with `:`, YAML 1.1 boolean keys and leading-zero numbers it had never generated; all three are now generated and rejected.
- Check (h) accepts only an unquoted `true` (YAML's `True`/`TRUE` spellings read the same) for the four slash skills, since Claude Code before 2.1.218 recognises nothing else; check (g) accepts only an absent key or the literal `false` on the router, in both the typed and the string view, since Claude Code also reads yes/on/1 and numbers such as `1.0` as true. ## [1.4.0] - 2026-10-06

Plugin-shell upgrade to the current `harness-devtools:plugin-upgrade` baseline and the official plugin reference ([#138](https://github.com/PsychQuant/psychquant-claude-plugins/issues/138), parent PsychQuant/che-msg#39). No binary change — the wrappers still pin `DESIRED_VERSION` 0.5.0.

### Changed
- **Behavior change:** `commands/{auth,chats,search,send}.md` are now skills (`skills/<name>/SKILL.md`), invoked as `/che-telegram-mcp:<name>` (the bare `/auth` still works while no other command uses the name). They set `disable-model-invocation: true`, so Claude no longer invokes them on its own — up to 1.3.2 these were commands that Claude could also load by itself. The same setting also stops scheduled tasks whose prompt is one of these skills, and subagent skill preloads, from running them. Natural-language requests go through `telegram-messaging`, which stays model-invocable.
- The wrapper tests (`test-wrapper-mcp-error.sh`, `test-wrapper-pid.sh`) moved out of the shipped plugin to `tests/che-telegram-mcp/` in the marketplace repo, so only the two wrappers remain in `bin/` and on the Bash tool's `PATH`.
- The wrappers themselves stay in `bin/`, because the harness-devtools release tooling finds them only there: `plugin-binary-meta.sh` (used by `plugin-update`) scans `bin/` and `hooks/`, and `plugin-deploy`'s release gate globs `bin/*wrapper.sh`. A move to `scripts/` was tried while preparing this release and reverted, because it made the `DESIRED_VERSION` pin detection and that gate silently stop working. A consequence is that the plugin still has `bin/`, so claude.ai and Cowork will not install it — which does not cost anything here, since both servers need a local TDLib binary and Keychain.
- `plugin.json` description now states the real tool counts (telegram-all 28, telegram-bot 31) instead of "28+".

### Fixed
- `allowed-tools` in the four entry points named `mcp__che-telegram-mcp__*`, which matches no tool, so the pre-approval never applied. They now use `mcp__plugin_che-telegram-mcp_telegram-all__*`.
- SessionStart hook command quotes `${CLAUDE_PLUGIN_ROOT}` (the only `claude plugin validate` warning).

### Security
- **Net effect is a widening for `auth`, `chats` and `search`:** before, nothing was pre-approved (the names were wrong); now each skill pre-approves the tools it lists, but only for the turn in which it is invoked — the grant clears when the user sends the next message. For `auth` the list includes the credential-entry tools `auth_set_parameters`, `auth_send_phone`, `auth_send_code` and `auth_send_password`; in practice the later steps happen after the user has replied with a phone number or code, so they usually go through the normal permission settings anyway. The marketplace-repo test `tests/che-telegram-mcp/test-plugin-layout.sh` keeps this list on an explicit read-only allowlist (login steps only in `auth`).
- `send` deliberately does not pre-approve `send_message`, because a sent message cannot be recalled. That leaves `send_message` under the user's normal permission settings: in the default permission mode Claude Code asks before sending; in `bypassPermissions` or auto mode, or with an allow rule for the tool, it does not, and the skill's instruction to confirm the recipient and text first is the only remaining guard.

## [1.3.2] - 2026-05-22

### Fixed
- `che-telegram-all-mcp-wrapper.sh`: lock-refused branch now emits a JSON-RPC 2.0 error envelope to stdout before exiting, so Claude Code's MCP client parses the human-readable message + structured data instead of seeing only `-32000 Server error`. Envelope carries:
  - `error.code: -32000` (JSON-RPC server-defined errors range)
  - `error.message: "Another instance of CheTelegramAllMCP is already running (lock held by PID NNNN). Use the existing Claude Code window, or kill the previous wrapper first."`
  - `error.data.lockHolderPid: <pid>` (machine-readable lock holder)
  - `error.data.recoveryCommand: "pkill CheTelegramAllMCP 2>/dev/null; rm -rf ~/.cache/che-telegram-all-mcp.lock ~/.cache/che-telegram-all-mcp.lock.flock"` (semicolon, not `&&`, so cleanup runs even when no process exists)
  - `error.data.docsUrl: https://.../README.md#multi-session-limitation`

  The original stderr message is retained for direct-shell debug.

  **PR-1b id matching (added 2026-05-22 after empirical verification)**: wrapper reads the first line of stdin (with 2s timeout) to extract the JSON-RPC `initialize` request's `id` field, then emits the response envelope with **matching id**. This was required because empirical two-session reproduction in Claude Code v2.1.148 showed that `id: null` responses (the v1.3.2 first attempt) are not matched to pending `initialize` requests and don't surface in Claude Code's MCP error state. With matching-id (PR-1b), debug-log capture confirmed Claude Code's MCP client correctly parses the envelope + stores the full `error.message` internally.

  Stdin extraction uses `jq` when available (preferred) and a bash regex fallback for environments without jq. Handles MCP 1.0 spec id forms: integer, quoted string, or null.

  New `test-wrapper-mcp-error.sh` covers 6 cases: happy path / lock refused emits valid JSON / stale-lock self-recovery / recoveryCommand validation / id-matching with initialize request / timeout fallback to null. Resolves [#31](https://github.com/PsychQuant/che-msg/issues/31).

  **Known UX gap** (out of plugin scope): Claude Code's `/mcp` short-list UI may display only `-32000` (truncated form) instead of the full message. The full message IS captured in Claude Code's internal MCP error state (verified via `--debug mcp` debug logs) and is available to downstream tool consumers. The display truncation is a Claude Code UI policy concern, not a plugin issue.

### Documentation
- `README.md`: added `## Multi-session limitation` section explaining the TDLib single-instance constraint, the v1.3.2+ human-readable error message, and a recovery cookbook (`pkill CheTelegramAllMCP 2>/dev/null; rm -rf ~/.cache/che-telegram-all-mcp.lock ~/.cache/che-telegram-all-mcp.lock.flock`). ## [1.3.1] - 2026-05-07

### Fixed
- `che-telegram-all-mcp-wrapper.sh`: add atomic-claim lock (flock with mkdir fallback) before PID-tracking section.
